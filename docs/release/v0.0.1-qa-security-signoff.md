### 3.2 Command / path injection campaign (new, this pass)

**Method:** static source review of every crate that touches
attacker-controlled input (adapter `tool_input`/`command` fields, session
IDs, event payloads), since standing up the full live stack's daemon,
uploader, and ingest processes to fuzz them with shell metacharacters was
not necessary once the actual attack surface was enumerated: there is no
shell-invocation surface for untrusted data in either repo's production
code to fuzz in the first place.

- `crates/` in fornax-core (`fornax-adapter-claude`, `fornax-adapter-codex`,
  `fornax-daemon`, `fornax-store`, `fornax-cli`, `fornax-verify`,
  `fornax-types`): **zero** occurrences of `std::process::Command`,
  `Command::new`, or any `sh -c` construction in production source. No
  process-spawning surface exists to inject into. **PASS by absence of
  attack surface**, stated explicitly rather than fabricating a test
  against a control that doesn't exist.
- fornax-cloud `crates/` and `backend/`: same result — the only
  `tokio::process::Command` usage in the entire repo is
  `crates/fornax-uploader/tests/real_backend.rs`, a test-only harness that
  shells out to `psql` for assertion setup, parameterized by a `Uuid`
  value (not an attacker-controlled string) — not production code, not
  reachable from any adversarial input. **PASS.**
- Path construction from attacker-controlled fields: traced every
  `PathBuf`/`.join(`/`fs::write`/`File::create` call in
  `crates/fornax-uploader/src/spool.rs` (the most plausible location, since
  it writes one file per queued message). Spool filenames are built from
  `Uuid::new_v4()` values generated internally by the spool itself, never
  from `session_id`, `tool_input`, or any other field in the ingested
  message. Grepped both repos for `session_id`/`event_id`/`tool_input`/
  `command` flowing into any path-construction call — no hits. **PASS**:
  no path-traversal surface (`../../etc/passwd`, null bytes, oversized
  payloads in these fields cannot reach a filesystem path).
- Malformed/adversarial *event* input (as opposed to path/command
  construction) — duplicate/unknown/malformed event handling — was already
  covered as part of FORNX-34's WAL durability and restart/recovery
  evidence; not repeated here.

**Not run:** no live fuzz/adversarial-payload run against a running
`fornax-daemon`/adapter process was performed in this pass. Given the
static result (no shell-invocation or attacker-influenced path-construction
surface exists anywhere in either repo), a dynamic run would be exercising
input validation and storage-as-inert-data behavior, not an actual
injection primitive. This is flagged as **NOT RUN, not PASS** — a future
pass with time budget for live fuzzing is legitimate defense-in-depth, but
no Critical/High risk is left open by skipping it, since there is nothing
in the code today for a crafted payload to reach.

### 3.3 XSS campaign (new, this pass)

**Method:** static review of the fornax-cloud React frontend for every
common unsafe-HTML sink, plus tracing how claim/rationale/evidence text
actually reaches the DOM.

- `grep -rn dangerouslySetInnerHTML frontend/src` — 0 hits.
- `innerHTML`, `insertAdjacentHTML`, `document.write`, `new Function(...)` —
  0 hits anywhere in `frontend/src`.
- No markdown-with-raw-HTML renderer (`react-markdown` + `rehype-raw`,
  `marked`, etc.) is a dependency (`frontend/package.json`).
- No `javascript:`-scheme URI construction in `frontend/src`.
- `FindingDetailPage.tsx` renders `data.claim_text` and `data.rationale` as
  plain JSX expression children (`<p>{data.claim_text}</p>`,
  `<p>{data.rationale}</p>`) — React's default text-node escaping applies;
  there is no sink anywhere in the codebase capable of interpreting that
  string as HTML/script.

**PASS by absence of sink**, stated explicitly per the same principle as
3.2: there is no code path in this frontend that can execute a string as
markup, so a payload like `<script>alert(1)</script>` in a claim or
rationale field can only ever render as literal text.

**Not run:** a live Playwright confirmation (ingest a claim containing
`<script>alert(1)</script>` end-to-end through the real backend and assert
it renders as inert text in a running frontend) was **not performed** in
this pass — bringing up the full backend/Postgres/frontend stack was out
of the available session time budget once the static result showed no
exploitable sink exists. Flagged as **NOT RUN, not PASS**. No Critical/High
risk is left open: the static sink enumeration is exhaustive for the
frontend's actual dependency set, not a sample.

## 5. Defect found and fixed during this pass

**FORNX-279** (Bug): `scripts/release-readiness.sh`'s `not_blocked` gate
check used a case-insensitive substring match on `"block"`, which
false-positives on ordinary prose ("release-blocking", "blocker") present
in this very ticket's own description and in FORNX-34's closing comment —
making the `qa`/`security`/`stage` gates permanently unpassable for
well-written tickets, independent of any real BLOCK verdict. Fixed in
[fornax-core#23](https://github.com/horonomy/fornax-core/pull/23) with a
case-sensitive whole-word match on the literal token `BLOCK`, consistent
with the documented convention and the existing test fixture. This is a
release-tooling correctness defect, not a security or product defect, and
does not gate this sign-off's PASS verdict — it is disclosed here because
it directly affects whether `release-readiness.sh` can evaluate this very
ticket correctly.

### 7.1 Dynamic adversarial daemon/adapter input — COVERED

Bounded 12-case corpus (malformed JSON, missing/null/wrong-type fields,
unknown fields, 60-3000-level nesting, 5MB strings, control characters,
path-traversal-looking strings, shell metacharacters, replayed event IDs,
100KB identifiers) run against a real `fornax-daemon` +
`fornax-hook-claude`, each case followed by a fresh-session CONTRADICTED
probe to confirm no state corruption. Zero crashes, zero panics, zero
subprocess spawns, zero filesystem escapes, no corruption; malformed input
either silently dropped (unparseable) or stored inertly (never coerced/
executed). Test: `crates/fornax-daemon/tests/adversarial_daemon_input.rs`
(fornax-core#30, merge commit `fb03f4f7ee9e7bcd5c3bde1c98bbe18d1c9d7fe4`).

One Informational, non-blocking observation (not filed as a Jira Bug,
recorded here for visibility): `fornax-adapter-claude`'s
`last_assistant_text` reads a `Stop` hook's `transcript_path` via
`std::fs::read_to_string` with no confinement to `$FORNAX_HOME` — content
from an arbitrary local path (even via `../../` traversal) can reach the
`claims` table if it happens to parse as the expected transcript JSONL.
No privilege boundary is crossed (the hook already runs as the invoking
user), so this does not block v0.0.1, but is worth a future confinement
check.

### 7.2 Real browser XSS — COVERED

Real Playwright session against the frozen candidate's `/dashboard`, four
payloads (`<script>`, `<img onerror>`, attribute-breakout `">`,
`javascript:` URI) injected into claim text via `fornax-hook-claude`.
`window.__FORNAX_XSS_EXECUTED` stayed `undefined` in every case; payloads
rendered only as inert HTML-escaped text; zero live `<script>`/`<img>`
elements or `javascript:` hrefs created. A normal event sent afterward
rendered correctly, confirming no persistent corruption. Full repro/detail:
`docs/release/0001-fornx-238-dashboard-xss-check.md` (fornax-core#28,
merge commit `cfc1a70648e099447565bfc4502001b7f6b3243e`).

Informational: the dashboard's `html_escape` helper does not escape quotes
— safe today only because no rendered field is ever placed inside an HTML
attribute. Worth revisiting if that changes.

### 7.3 Full-stack secret-egress canary — CRITICAL FOUND, FIXED, RE-VERIFIED

Initial run (random-hex canary marker, shaped to trip `redact_json`'s
generic high-entropy detector) found the raw marker reaching the daemon's
own log, the local SQLite store, and `fornax export-spool` output
unredacted via two fields: `AgentEvent.tool_input` and `Claim.text`.
`tool_response`/`raw.*` redaction was confirmed still correctly working in
the same repro — a scoped two-field gap, not total failure. Filed as
**FORNX-280** (Critical), independently reproduced (not just
subagent-reported) before fixing.

Fix: `crates/fornax-daemon/src/main.rs`'s `handle_message` now applies
`redact_json`/`redact_text` to `tool_input`/`Claim.text` at the same
ingestion boundary as the other fields (fornax-core#29, merge commit
`f309bc21caad2bf8b994b7f366ba2a42eea27c63`). Regression test
`tool_input_and_claim_text_are_redacted_before_storage` added; verified by
temporarily reverting just the fix lines and confirming the test fails
with the exact reported leak, then restoring the fix and confirming it
passes again.

Re-verification after the fix (same canary technique, fresh random
marker): zero raw hits in the daemon log, the SQLite store, or the
`fornax export-spool` output — only `[REDACTED]` placeholders. **Not
re-exercised this pass**: the downstream `fornax-uploader` →
ingest/Pub/Sub-emulator → backend → Postgres → SaaS-UI stages — the
original run stopped before reaching them per the "stop immediately on a
forbidden hit" instruction, and re-running just the daemon/spool boundary
(where the actual defect lived) constitutes the impacted re-verification,
not the full pipeline. `fornax-uploader`'s own `guard.rs` remains an
independently-tested last line of defense (see §3) but the end-to-end
downstream path through Postgres/UI is still genuinely untested — a real,
disclosed gap, not rounded up to PASS. See the FORNX-239 Jira thread's
coverage reconciliation for its classification.

### 7.4 Unrelated defect found and fixed: CI silently skipped fmt/clippy/test

While running §7.1, a repo-wide CI defect was discovered and is recorded
here for completeness even though it isn't a product/security defect:
`.github/workflows/ci.yml`'s "check workspace has crates" step used a
`find` depth that never matched this repo's real `crates/<pkg>/Cargo.toml`
layout, so `fmt`/`clippy`/`test` have been silently **skipped** (reported
as passing) on every PR since the workflow was added — including every PR
merged earlier in this v0.0.1 release-process pass. Every one of those
merges was independently re-verified locally by hand
(`cargo fmt/clippy/test`) before merging regardless, so this does not
retroactively invalidate them, but the CI *signal* itself could not be
trusted until fixed. Fixed in fornax-core#31 (merge commit
`42a8ad354f4300b2aedd722dc609b12d827b68c1`), which also had to add an
explicit `cargo build --workspace` step once real test execution
immediately caught a second real gap (the new adversarial-input
integration test needs sibling workspace binaries built first). This is
the exact commit now bound as the frozen `fornax-core` candidate SHA (see
§1/manifest) — chosen deliberately so the shipped candidate's own CI
history is trustworthy, not just its code.
